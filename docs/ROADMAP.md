# 구현 순서

1. 초기 수집 확인: `wire.jsonl` 허용 이벤트 추출, 파일 오프셋 기반 증분, `inspect`·`summary`·`validate` 명령을 구현했습니다.
2. 수집·신뢰도 확보: 장기 관찰로 집계의 정확성을 확인합니다. 관찰 포인트는 다음과 같습니다.
   - 2026-10-15 실측(6시간, 73샘플): 공식 쿼터 채널(로컬 REST `GET /api/v1/oauth/usage`, Bearer)을 확보하고 `quota` 명령을 추가했습니다. 반나절 이상의 실사용에도 모든 창의 `usedRatio`는 0을 유지했고, `limit5h`의 `resetAt`은 고정 5시간 버킷 경계에서만 점프했습니다(10:19:08Z → 15:19:08Z). 이 계정의 소비가 이 계량기에 잡히지 않는다고 판정해 제품 피드백 대상으로 두고, `usedRatio` 전환이 생기면 장기 관찰로 감시합니다.
   - `inputCacheCreation`이 항상 0인지, 아니면 실제로 값이 쌓이는지
   - 세션 재개(resume) 시 기존 파일에 이어 쓰는지, 새 파일을 만드는지, 재개로 같은 사용량이 중복 기록되는지
   - 이벤트가 append 형태로만 쓰이는지(기존 줄이 바뀌거나 잘리지 않는지)
   - `token_counting.measured`와 `usage.record`의 1:1 대응과 합계 일치가 계속 유지되는지
   - `usage.record` 합계와 `agent.message.appended` 메시지 사용량 합계의 차이 원인 규명
   - 관측 절차와 통과 기준은 `usage_monitor_codex`의 fieldtest 절차서 형식을 따릅니다.
3. 저장: SQLite 스키마 버전, 파일 오프셋과 문맥 저장, 파일 교체·잘림·재시작 복구를 구현합니다. `usage.record`에 식별자가 없으므로 파일 신원+오프셋으로 중복 제거를 유지합니다.
4. 로컬 서버·대시보드: HTTP 화면, 기간별 토큰 차트, 모델별·에이전트별 분포, 캐시 비중, 검증 리포트 표시를 구현합니다.
5. Windows 운영: 트레이 위젯, 자동 실행, 설치·제거를 구현합니다.

현재는 화이트리스트 파싱, 오프셋 증분 스캔, 합계·일별·모델별·에이전트별 집계, 내재 대조 리포트까지 구현했습니다. SQLite 저장, 로컬 서버, 위젯, 자동 실행은 후속 단계입니다. 각 단계는 필요한 검증을 마친 뒤 완료로 표시합니다.
